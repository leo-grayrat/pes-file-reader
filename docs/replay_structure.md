# PES2021 回放（REPLAY）data 块结构分析

> 分析对象：`examples/rep/REPLAY00000000~00000031`（50 个，十六进制编号）经
> `pes_decrypt.py` 解密后的 data 块，存放于 `decoded/rep_REPLAY*.data`。
> 分析脚本：根目录 `replay_analyze.py`（子命令：`entropy` / `strings` / `header` /
> `consensus` / `period` / `tail` / `records` / `fields`，默认 `all`）。
> 本文档如实记录当前进展，分【已确认】【疑似】【未解】三档。

## 样本统计

| 项目 | 数值 |
|------|------|
| 样本数 | 50 个回放（编号 00~31，十六进制） |
| 原始文件大小 | 均为 5,383,087 字节（加密后） |
| data 块大小 | 均为 5,368,928 字节（0x51EC60），50/50 一致 |
| 外层布局 | 320(加密头)+208(文件头)+384(desc)+13157(logo)+5368928(data)+90(serial)，合计 5,383,087，零误差 |
| serial 区 | 占字节数 = 头字段 `serialLength`(45) × 2（按字符计长，已校正） |
| description | 仅含回放序号 01~50，无比赛元数据 |
| serial | 50 个样本完全相同（同一主机的序列号） |
| data 整体熵 | 约 6.15（非加密态；32.1% 为 0x00 字节，无 ≥4KB 的连续同值填充段） |

## 一、已确认（多样本验证、可直接用于解析）

### 1.1 data 块头部（0x00~0x7F，与 BL/ML 的 data 头同构）

| 偏移 | 值（50 样本） | 含义 |
|------|---------------|------|
| `+0x00` | `13`（恒定） | 类型标识 = REPLAY（BL=11、ML=10，与交接文档一致） |
| `+0x04` | `80`（恒定） | 头部自身大小 0x50（BL/ML 亦为 80） |
| `+0x08` | `5368848` = 0x51EC10（恒定） | **自洽字段：恒等于 data 块大小 − 0x50**，即负载长度 |
| `+0x0C` | 10401/10500/10600/10700/10702，随比赛变化 | 与 `+0x10` 强相关（见 1.2） |
| `+0x10`/`+0x14` | 400/500/600/700（两者恒相等），随比赛变化 | 疑似名单记录容量/参赛球员规模计数 |
| `+0x20` | `48`（恒定） | 固定，含义未知 |
| `+0x30~0x50` | 32 字节，样本间全变 | 哈希/校验区（与 BL/ML 同位置行为一致） |

### 1.2 `+0x0C` 与 `+0x10` 的相关性（50 样本全量）

```
(+0x0C, +0x10) 组合：
  (10401, 400) × 3    (10500, 500) × 4    (10600, 600) × 2
  (10700, 700) × 40   (10702, 700) × 1
```

一一对应、无例外。规律形如 `+0x0C ≈ 10000 + +0x10`（存在 10401、10702 两个微偏差，
可能是编码细节而非噪声）。语义未定，但作为配对字段可信。

### 1.3 名单记录数组（0x80 起，步长 0xA0，名字在记录内 +0x58）

- 每条记录 **0xA0 (160)** 字节；名字为 9 字节大写 ASCII，位于记录内 `+0x58`。
- 记录前 2 个 u16 构成"魔数"，标识所属阵营：
  - 样本0：`0x2CBDFFFD`×11（皇家社会首发：A. REMIRO / LE NORMAND / ZUBELDIA /
    GOROSABEL / MONREAL / ILLARRA / SILVA / MERINO / PORTU / OYARZABAL / ISAK），
    `0x247AFFFE`×11（对手首发）。
  - 样本1：`0x254EFFFD`×11 + `0x17BBFFFE`×11（完全不同的两套阵容）。
  - 低 16 位疑似队伍 ID，最低字节 `FD`=主队 / `FE`=客队（推测，见二档）。
- 记录 `+0x04` 处为 4 字节整数，多数为 5~6 位（如 106956、122111），疑为**球员 ID**。
  个别记录该字段呈现为浮点值（如 `0x433C0000`≈188.0），疑为身高，字段布局尚未精确切分。
- 第 22~24 条（`0x80+0xA0*22~24`）魔数 `0x0000FFFF`，名字 `REFEREEA/B/C`，
  `+0x04` 为 1/19/16 之类小整数（裁判编号/风格）。
- 其后为若干全零的 `0x0000FFFF` 占位记录；`0x80+0xA0*39` 处出现一次 `0x00402236`
  （数组收尾标志，样本间取值不同）。
- 两样本同位名字对比：样本0 vs 样本1 仅 18/40 同位相同 → **名单随比赛变化，非固定模板**。

### 1.4 全局长度公式

```
原始文件 = 320 + 208 + 384 + 13157 + 5368928 + 45×2 = 5383087 ✓（50/50）
data 内：+0x08 = len(data) − 0x50 ✓（50/50）
```

## 二、疑似（有证据支撑但未闭环验证）

1. **稀疏关键帧区（约 0x1000~0x3F00）**：大片 0 填充中散布
   `FF FF 00 … 34 43` 模式的 16 字节小结构（`0x34 43 00 00` = float32 180.0），
   间距不规则（出现过 0xA0、0x100 相邻实例），疑为球/镜头关键帧或场景标记。
2. **全名/长字符串表（约 0x1D00~0x3600）**：出现 `NACHO MONREAL`、`ILLARRA` 等
   全名（名单区只有 ≤9 字节缩写名），且非零字节密度呈波浪分布；该区间内还混有大量
   小写字母"伪字符串"（`wSwzw`、`uyvgw`…），**更像被某种替换/异或扰码的数据**，
   不建议当明文处理。
3. **队名出现点**：样本0 中 `REAL`（来自 REAL SOCIEDAD）命中 3 处
   （0x35B、0x2905、0x324A），均落在长字符串表范围内 → 该表兼含队名。
4. **事件/运动流主体（约 0x4000~0x51EBDF）**：16KB 熵从 2.80（头部区）跳变到 6.15
   并一直保持；内容含重复模式 `EF 0A CC 00 33 01 19 02`、成组的小幅 u16（带符号，
   如 `FE FF`、`B2 FF`），符合"每帧球员坐标增量/事件包"特征；但**记录边界与
   字段语义均未破解**。样本0 vs 样本1 差异率 76.99%，说明此区承载比赛差异主体。
5. **尾部固定尾标（0x51EC10~0x51EC60）**：
   - `[0x51EC10, 0x51EC3A)` 恒为 `00…`（0x2A 字节，3 个样本一致）；
   - `+0x3A` 处恒为 `08 18`（疑似结束魔数）；
   - 其后 12 个 i16（样本间变化，形如 `F3 00 B4 FF EE FF …`），最后 9 字节 0 填充。
   - 恰好 `+0x08`(0x51EC10) 指向该零填充段起点 → "负载长度"自洽闭环。
6. **头部 `+0x68~+0x7C` 小整数**（样本0：20/1/9/2/255/25；样本1：10/…/10/2/255/25），
   疑为阵型人数、换人数、难度等比赛参数。

## 三、未解

1. 事件流（0x4000~0x51EBDF，约 5.24MB，占 data 97.6%）的记录格式：
   无步长周期（候选步长 4~4096 及 0x690 的差异余数集中度均 <6%，自相关亦无峰值），
   推测为变长事件包，需结合游戏逻辑或动态调试定位。
2. `+0x54`=15008、`+0x58`=8112、`+0x60`=660、`+0x64`（每样本不同，1922~36481）
   的语义；`+0x64` 疑为随机种子或事件计数。
3. 记录内浮点字段的确切布局（哪个是身高/坐标/能力值）。
4. 长字符串表的扰码方式（若有）与完整字段表。
5. `+0x30~0x50` 哈希算法（修改器实操时需确认游戏是否校验）。

## 四、跨样本共识分析说明

- 5 样本按位 AND/OR 共识：**28.32% 字节恒定**；恒定 run 多为名单记录内的浮点模板
  （如 `[0xE1,0x115)`、`[0x183,0x1C0)` 等，长度 51~83 字节，周期 0xA0），
  说明名单记录骨架（能力浮点默认值）跨比赛稳定，变的是名字/ID/首发选择。
- 变化最集中的 64KB 桶分散在 0x90000、0xB0000、0x1B0000~0x1E0000、0x2E0000~0x2F0000，
  即事件流内部无单一热点，符合"整段都是比赛数据"的判断。

## 五、下一步建议

1. 以 `+0x10/+0x14` 的 400/500/600/700 为线索，检查名单记录数组是否真的延伸到
   `0x80 + 0xA0×N`（N 取该计数）处，确认容量语义。
2. 对事件流做"已知比分/事件时间锚点"对照：先在游戏里记下某回放的进球时间点，
   再在数据中搜索对应帧号/时间戳的整数表示。
3. 用 22~24 条裁判记录与 12 个尾部 i16 做修改器最小实验（改值→重加密→进游戏
   验证是否被读取/校验）。
4. 若继续纯静态分析，优先攻 `0x4000` 起始处的 `93 20 CE 2A 00 00 87 03 …` 序列，
   疑似事件流目录/索引（其后紧跟重复的 `EF 0A CC 00 33 01 19 02` 三元组）。

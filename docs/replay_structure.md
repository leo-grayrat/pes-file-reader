# PES2021 回放（REPLAY）data 块结构分析

> 分析对象：`examples/rep/REPLAY00000000~00000031`（50 个，十六进制编号）经
> `pes_decrypt.py` 解密后的 data 块，存放于 `decoded/rep_REPLAY*.data`。
> 分析脚本：根目录 `replay_analyze.py`（子命令：`entropy` / `strings` / `header` /
> `consensus` / `period` / `tail` / `records` / `fields` / `boundary` / `headseg` /
> `frames` / `events`，默认 `all`）。
> 本文档如实记录当前进展，分【已确认】【疑似】【未解】三档。
> 本轮（任务 #11）结合 `docs/exe_analysis.md` 的 exe 静态分析锚点（回放写出例程
> 0x01FDC500：`0x3AA0 + 0x51B1C0 = 0x51EC60` 拆分）完成了分段边界验证，
> 并**破解了事件流的帧网格结构**。

## 一、已确认（多样本验证、可直接用于解析）

### 1.1 data 块头部（0x00~0x7F，与 BL/ML 的 data 头同构）

| 偏移 | 值（50 样本） | 含义 |
|------|---------------|------|
| `+0x00` | `13`（恒定） | 类型标识 = REPLAY（BL=11、ML=10，与交接文档一致） |
| `+0x04` | `80`（恒定） | 头部自身大小 0x50（BL/ML 亦为 80） |
| `+0x08` | `5368848` = 0x51EC10（恒定） | **自洽字段：恒等于 data 块大小 − 0x50**，即负载长度 |
| `+0x0C` | 10401/10500/10600/10700/10702，随比赛变化 | 与 `+0x10` 强相关（见 1.2） |
| `+0x10`/`+0x14` | 400/500/600/700（两者恒相等），随比赛变化 | 疑似名单记录容量/参赛球员规模计数 |
| `+0x20` | `48`（恒定） | 固定，含义未知 |
| `+0x30~0x50` | 32 字节，样本间全变 | 哈希/校验区（与 BL/ML 同位置行为一致） |
| `+0x54` | `15008` = 0x3AA0（**50/50 恒定**） | **名单/头部段长度**（本轮新解，见 1.4） |
| `+0x58` | `8112`（**50/50 恒定**） | **事件流帧大小**（本轮新解，见 1.5） |
| `+0x60` | `660`（**50/50 恒定**） | **事件流帧数**（本轮新解，见 1.5） |

### 1.2 `+0x0C` 与 `+0x10` 的相关性（50 样本全量）

```
(+0x0C, +0x10) 组合：
  (10401, 400) × 3    (10500, 500) × 4    (10600, 600) × 2
  (10700, 700) × 40   (10702, 700) × 1
```

一一对应、无例外。规律形如 `+0x0C ≈ 10000 + +0x10`（存在 10401、10702 两个微偏差，
可能是编码细节而非噪声）。语义未定，但作为配对字段可信。

### 1.3 名单记录数组（0x80 起，步长 0xA0，名字在记录内 +0x58）

- 每条记录 **0xA0 (160)** 字节；名字为 9 字节大写 ASCII，位于记录内 `+0x58`。
- 记录前 2 个 u16 构成"魔数"，标识所属阵营：
  - 样本0：`0x2CBDFFFD`×11（皇家社会首发：A. REMIRO / LE NORMAND / ZUBELDIA /
    GOROSABEL / MONREAL / ILLARRA / SILVA / MERINO / PORTU / OYARZABAL / ISAK），
    `0x247AFFFE`×11（对手首发）。
  - 样本1：`0x254EFFFD`×11 + `0x17BBFFFE`×11（完全不同的两套阵容）。
  - 低 16 位疑似队伍 ID，最低字节 `FD`=主队 / `FE`=客队（推测，见二档）。
- 记录 `+0x04` 处为 4 字节整数，多数为 5~6 位（如 106956、122111），疑为**球员 ID**。
  个别记录该字段呈现为浮点值（如 `0x433C0000`≈188.0），疑为身高，字段布局尚未精确切分。
- 第 22~24 条（`0x80+0xA0*22~24`）魔数 `0x0000FFFF`，名字 `REFEREEA/B/C`，
  `+0x04` 为 1/19/16 之类小整数（裁判编号/风格）。
- 其后为若干全零的 `0x0000FFFF` 占位记录；`0x80+0xA0*39` 处出现一次 `0x00402236`
  （数组收尾标志，样本间取值不同）。
- 两样本同位名字对比：样本0 vs 样本1 仅 18/40 同位相同 → **名单随比赛变化，非固定模板**。
- **全名已解（本轮新确认，见疑似 1 修正）**：名单段内 [0x2800, 0x2E00) 为
  **明文全名表**，22 个全名按序与前 22 条首发记录一一对应（50/50 样本均成立，
  `decode_dump.py` 全量提取）；带连字符长名（如 MILINKOVIĆ-SAVIĆ）因含非 ASCII 字符
  被切成两段，需把以 `-` 开头的片段并回前一条。
- 本轮补充：样本0 在 [0x80, 0x3AA0) 按 0xA0 网格共 93 个记录位，其中 **72 个非零**
  （首发 11+11 + 裁判 3 + 替补/其他实体若干 + 记录内 `3F800000`(float 1.0) 等模板值）。

### 1.4 二级分段：名单/头部段 0x3AA0 + 事件流 0x51B1C0（50/50 闭合）

- exe 写出例程（`docs/exe_analysis.md` ①，文件偏移 0x01FDC500~0x01FDC600）给出
  `0x3AA0(15,008) + 0x51B1C0(5,353,920) = 0x51EC60` 拆分；数据侧验证：
  - 50/50 样本 `len(data) == 0x3AA0 + 0x51B1C0`；
  - **头部 `+0x54` 恒等于 0x3AA0（50/50）**——头部自带该分段长度，自洽闭环；
  - [0, 0x3AA0) 内最后非零字节：样本间 0x3657~0x38F6，均在段内，段尾为零填充；
  - 0x3AA0 处存在清晰结构突变：以 0x100 窗、0x40 步长滑动，熵从 0.0（纯零区）
    经 0.53→2.55→6.29 快速爬升，跨样本差异率同步从 0% 跳至 ~80%。
- 名单/头部段内部布局：0x80~(约)0x1980 记录数组，**[0x2800, 0x2E00) 为明文全名表**
  （22 条，与首发记录一一对应，本轮新解，见疑似 1 修正），段内其余长字符串区混有
  伪字符串，0x3980 之后纯零填充至段尾。

### 1.5 事件流帧网格：660 帧 × 8112 字节（50/50 闭合）

- **头部 `+0x58`(8112) × `+0x60`(660) = 5,353,920 = 0x51B1C0，50/50 精确闭合**——
  事件流不是无结构的变长流，而是**定长帧数组**。
- 每帧 8112 字节，内部布局（样本0 全 660 帧验证）：

| 帧内偏移 | 长度 | 内容 |
|----------|------|------|
| `+0x00~0x0F` | 16B | 帧头。字节 [1:3] 为 **u16 比赛时钟**（单调递增，相邻步长 5 或 10，全场恰好回绕一次；样本0 为 +10×289 / +5×368，疑与回放倍速/暂停有关）；字节 4~15 为小整数状态字段（如 `05 00 13 13 40 00 02 00 04 3A 36 00`，随比赛阶段微变） |
| `+0x10~0xFFF` | 4096B | **状态表：256 条 × 16B**。样本0 帧0 有 229 条非零；条目含成对 u16 字段与偶发的 `3F800000`(float 1.0)；帧间同位相同率约 52%（逐帧变化的实体状态快照） |
| `+0x1010~0x1FB0` | 4000B | **事件区**，见 1.6 |

- 事件流首 4 字节（帧0 时钟高 16 位 + 低 16 位）跨样本各不相同（如样本0 =
  `00 17 7F 47`），随录制时刻变化，与"比赛内时钟"一致，非全局墙钟。

### 1.6 事件区：16B 子头 + 10 个球员槽包（槽间距恒 300 字节）

- 事件区头 16B：`u16@+0`（191~204 间小整数，帧间波动）、`u16@+2`（**全场单调递增**，
  样本0 为 92→1388，疑为比赛进度计数）、`u16@+4`（{685, 1388} 二值，疑为阶段上限：
  上半场计数到 685 后进入下半场直至 1388）、`+8~+16` 恒为 `01 00 00…`（660/660）。
- 槽标记 `00 00 01 XX`（2 ≤ XX ≤ 40）：样本0 每帧稳定 **10 个槽，槽号 12~21**
  （帧 0~659 抽样全部一致；个别帧 11 个，多出槽 11；跨样本结构相同）。
- **槽间距恒 300 字节**（帧0 全 9 个间距均为 300）。
- 槽内结构：12B 头（`01 XX 00…`，个别槽头 +6 处带 `98 4C 4C` 等标记）+
  **20×i16 小整数序列**（逐帧变化，样本0 槽12 帧0/1/2 仅 4/20 相同，疑为姿态/动画码）+
  约 248B **高熵 blob**（熵接近随机，疑为压缩或加密的运动轨迹数据）。
- 已按上述规则切出前 100 个槽包并逐条给出候选解读（`python replay_analyze.py events`）。

### 1.7 全局长度公式

```
原始文件 = 320 + 208 + 384 + 13157 + 5368928 + 45×2 = 5383087 ✓（50/50）
data 内：+0x08 = len(data) − 0x50 ✓（50/50）
```

## 二、疑似（有证据支撑但未闭环验证）

1. **名单段中的长字符串表（约 0x1D00~0x3600）——本轮重大修正**：其中 [0x2800, 0x2E00)
   子区为**完整明文全名表**（22 个全名，如 `NACHO MONREAL`、`MIKEL OYARZABAL`），
   与记录数组前 22 条首发按序一一对应（50/50 样本闭合），此前“疑扰码、不建议当明文处理”
   的结论**作废**；带连字符且含非 ASCII 字符的长名会被切成两段，解析时需把以 `-` 开头
   的片段并回前一条。该区间其余部分仍混有小写字母伪字符串（`wSwzw`、`uyvgw`…），
   性质待查。
2. **队名出现点**：样本0 中 `REAL`（来自 REAL SOCIEDAD）命中 3 处
   （0x35B、0x2905、0x324A），均落在长字符串表范围内 → 该表兼含队名。
3. **帧头字节0**：多数帧为 0，样本0 帧24 起变 0x80 等；疑为时钟高位/标志位，
   与时钟步长切换（+10 → +5）同步出现，未闭环。
4. **状态表（256×16B）条目语义**：条目内成对 u16 值域集中（样本0 帧0 首位
   (0,0)×52、(0,0xFF)×6 等），含浮点模板；疑为每实体（球员+球+裁判+镜头）的
   逐帧状态，具体列语义未定。
5. **事件区 `u16@+2` = 比赛进度**：单调递增 92→1388，`u16@+4` 在 685 处换档，
   与"上下半场"叙事吻合，但未与真实比赛分钟数标定。
6. **槽号 12~21 的实体映射**：恰 10 个，疑为"持球相关球员 + 球"或关键实体子集
   （22 名球员中每帧只写 10 个），槽 16 头部额外带 `98 4C 4C` 标记（疑为守门员/球）。
7. **头部 `+0x68~+0x7C` 小整数**（样本0：20/1/9/2/255/25；样本1：10/…/10/2/255/25），
   疑为阵型人数、换人数、难度等比赛参数。
8. **尾部固定尾标（0x51EC10~0x51EC60）**：`[0x51EC10, 0x51EC3A)` 恒为 `00…`；
   `+0x3A` 处恒为 `08 18`（疑似结束魔数）；其后 12 个 i16（样本间变化，
   形如 `F3 00 B4 FF EE FF …`，位于最后一帧事件区内），最后 9 字节 0 填充。
   恰好 `+0x08`(0x51EC10) 指向该零填充段起点 → "负载长度"自洽闭环。

## 三、未解

1. **槽内 248B blob 的量化坐标语义（已部分解码，见 §七）**：blob 非加密、非 float32，
   而是「72×u16 计数器头 + 24×u16 结构化区（含量化坐标）+ 4B 枚举 + 52B 零尾」。
   剩余壁垒是结构化区各 u16 字段的**精确语义与量化比例尺**（uint16→场内坐标的轴/比例），
   需对照游戏内存或反汇编写出例程才能标定。这是事件流语义还原的最后一步。
2. 20×i16 姿态/动画码的字典（数值逐帧抖动，疑含动作编号+朝向+混合权重）。
3. 状态表（256×16B）各列语义。
4. `+0x54`=15008 已解，但 `+0x64`（每样本不同，1922~36481）语义仍未知；
   疑为随机种子或事件总数。
5. 名单记录内浮点字段的确切布局（哪个是身高/坐标/能力值）。
6. 长字符串表中全名表之外的伪字符串部分（若有扰码，方式未定）与完整字段表。
7. `+0x30~0x50` 哈希算法（修改器实操时需确认游戏是否校验）。
8. 球员 ID 与事件流的关联：名单 +0x04 的球员 ID 在事件流按 u32 检索零命中
   （随机期望亦≈0），事件流不直接引用球员全库 ID，改用槽号（12~21）等局部索引。

## 四、跨样本共识分析说明

- 5 样本按位 AND/OR 共识：**28.32% 字节恒定**；恒定 run 多为名单记录内的浮点模板
  （如 `[0xE1,0x115)`、`[0x183,0x1C0)` 等，长度 51~83 字节，周期 0xA0），
  说明名单记录骨架（能力浮点默认值）跨比赛稳定，变的是名字/ID/首发选择。
- 名单/头部段 [0, 0x3AA0) 5 样本恒定占比 72.07%（大量零填充拉高）。
- 变化最集中的 64KB 桶分散在 0x90000、0xB0000、0x1B0000~0x1E0000、0x2E0000~0x2F0000，
  即事件流内部无单一热点，符合"整段都是逐帧比赛数据"的判断。
- 帧0 vs 帧1：状态表相同 51.8%、事件区相同 51.0% → 帧间约一半字节为模板/重复结构。

## 六、blob 编码检测结论（2026-08-28，replay_zlib.py）

对 248B 高熵 blob（全 660 帧 6614 个）做编码探测，**排除标准压缩，并发现明文结构**：

1. **非 zlib/gzip/deflate**：blob 首字节分布均匀（0x78 仅 22/6614），
   `zlib.decompress`（zlib / raw-deflate / gzip 三种 wbits）前 40 个 blob **全部失败**。
2. **非强加密**：blob 首 4 字节存在**明文递增计数器**——槽12 跨 660 帧，第 2 字节 b1
   单调递增（相邻步长 0×432 / +1×105 / -1×105），第 4 字节 b3 先增后减；
   强加密不可能保留这种明文单调模式。
3. **相邻帧强相关**：同槽跨帧 blob 异或熵 3.87，显著低于本体熵 5.6（本体熵 5.35~5.94）。
4. **推断**：blob 大概率是「明文计数/时间戳头 + 运动数据（经轻度线性变换或 delta 编码，
   非标准压缩、非强加密）」。下一步应沿"剥掉头字段后对余下 240B 做同槽跨帧差分/异或"，
   观察是否有 float32 坐标/速度的低字节相关性；或反汇编写出例程 0x01FDC500 后续逻辑。

## 七、blob 内部布局（2026-08-30，probe_replay_blob*.py）

对**槽12 跨 660 帧**的 248B blob 做逐字节跨帧 XOR 熵 + uint16 重解 + hex 直视
（`probe_replay_blob.py` 修 `bi[2]→bi[1]` 崩溃后跑通，`probe_replay_blob2/3/4.py` 递进）。
**重要更正：§6.4 的 float32 坐标假设被证伪**——blob 内不含任何 float32，运动数据以
**uint16 量化（0–65535）**存储。

### 7.1 四区布局

| 区 | 偏移 | 长度 | 内容 |
|----|------|------|------|
| 头部 | `[0:144]` | 144B = 72×u16 | 每个 u16 的**高字节逐帧缓增（+1~+4/帧，计数/时间戳）**、低字节快速回绕（单帧内高熵，看似随机）。例 u16[0] 跨帧 59268→59432→59550→59667（步长 ~120–164，低字节回绕）。首字节 b1 单调不减占比 83%。→ 事件元数据/时间戳/ID 数组 |
| 结构化数据 | `[144:192]` | 48B = 24×u16 | 见 7.2 |
| 枚举字段 | `[192:196]` | 4B | 逐帧取多个 u32 值（0x00040111=262417 占 275 帧、0x00010155=65877 占 203 帧、其余零星），**非恒定**，疑为阶段/事件枚举 |
| 零填充 | `[196:248]` | 52B | 全零（660/660） |

### 7.3 编码结论（修正 §6 与早先 float32 猜测）

- blob **非加密**：头部 72 个 u16 计数器、结构化区 u16 时间戳、零尾均明文可见。
- blob **非 float32**：float32(LE) 重解全为 denormal（≈0），系 uint16 低字被误读；坐标为
  uint16 量化（或状态量）。
- 跨帧 XOR 熵 3.742（与 §6 的 3.87 一致）证实数值 delta/量化编码、逐帧强相关。
- **blob 内不存在可直接读取的 (x,y) 原始坐标对**（§7.5 坐标标定尝试为负结果）：
  结构化区 `[144:192]` 是「连续计数器/量 + 双峰状态标志 + 冗余别名偏移 + 常量0」的混合，
  坐标由游戏运行时从 20×i16 姿态/动画码（§1.6）重建，**不在 blob 里**。故无法仅靠「标定
  uint16→坐标比例尺」还原位置——须走姿态码/运行时映射。

### 7.4 开放项

1. 头部 72 个 u16 计数器的确切含义（是否含 RNG 种子/校验；首 u16 在帧100 出现非单调，
   疑因槽选取跨帧混入不同事件实例，需按事件身份稳定化后再做逐帧轨迹）。
2. 结构化区 `[144:192]` 各字段语义：连续偏移（u16#0/#2/#4/#5/#7/#8/#12/#14/#18/#22/#23）
   哪些是计数器、哪些是实体状态量；`+156` 零字段用途；冗余别名（u16#12=#14=#18=#22 值全同）。
3. 枚举字段 `[192:196]` 的取值枚举表与语义。
4. **坐标还原的真正路径**：20×i16 姿态/动画码（§1.6）的字典 + 游戏运行时映射，而非 blob 内缩放。

### 7.5 坐标标定尝试（2026-08-31，probe_replay_blob5.py，负结果）

把分析从「槽12 单槽」扩到 **10 槽(12~21) × 660 帧**，关键修正早先 slot-12-only 的偏差：

- **全部 24 个 u16 偏移都随槽变化**（无全局常量字段）；早先 slot-12 看成的「+156 恒0 /
  191/2296/203 常量模板」只是槽12 自身的值，跨槽即变 → 证实结构化区是**逐实体**的。
- 逐偏移离散度分三类：① **连续量**（u16#0/#2/#4/#5/#7/#8/#12/#14/#18/#22/#23，主峰占比 0–7%，
  满量程铺开）；② **双峰状态标志**（u16#11/#13/#16/#17/#20/#21，主峰≈191 占 17–25% + 次峰
  14–18%，即「8 默认 + 2 特殊」槽的标记）；③ **常量0**（u16#6=+156）。
- 用「球场长宽比 105:68≈1.544 + 两轴各向同性」找 (x,y) 坐标对：命中 20 对，但逐帧 10 槽散点
  **无一形成真实阵型**——候选「y」偏移全是双峰（8 槽≈200/~0.6m，2 槽≈2300/~7m）；退化对
  (u16#13,u16#21) 每槽 x≈y；frame0 时 x 全 0 的对亦存在。aspect 匹配纯属量程巧合。
- **唯一两轴皆铺开的对 (u16#4×u16#5)**：frame0 散点 x∈[4708,23347]、y∈[5,10995]；若按
  x 满量程对 105m（scale≈222 uint16/m）换算点云落在半场 [21,105]×[0,49]m，形似阵型但
  **未确认**（aspect 1.70≠1.544，亦可能是两个无关连续量）。列为弱线索，非结论。
- **结论**：blob 结构化区无干净原始 (x,y) 坐标场；坐标由运行时从姿态码重建。与 2026-08-30
  「回放是状态/动画流、非位置流」结论一致。标定比例尺之路在 blob 内走不通。

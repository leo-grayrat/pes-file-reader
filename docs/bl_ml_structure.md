# PES2021 BL/ML 存档 data 块结构文档

> 逆向对象：`examples/` 中 8 个解密后的 data 块（`decoded/`，只读）：
> `BL00000000~03.data`（一球成名）、`ML00000000/01/02/13.data`（大师联赛）。
> 大小约 19.5~19.7 MB，**各样本大小不完全相同**（尾部填充长度可变）。
>
> 结论分三档：**已确认**（有交叉证据）/ **疑似**（单一证据，待验证）/ **未解**（含下一步建议）。
> 所有偏移均相对解密后 data 块起点。多存档对比证据来自同一模式的
> 不同进度存档（BL0↔BL1、ML0↔ML13 等）。

## 一、已确认结构（有交叉证据）

### 1.1 头部（0x000 ~ 0x100）

8 样本全量核对（`bl_ml_probe3.py` 节一）：

| 偏移 | 内容 | 证据 |
|------|------|------|
| `+0x00` | u32 类型标识：BL=11，ML=10 | 8 样本一致 |
| `+0x04` | u32 = 80 | 8 样本一致 |
| `+0x08` | u32 = 0x015B6D44 (22768964) | 8 样本一致，疑格式版本 |
| `+0x0C` | u32 = 10700~10702 | **非常量**（交接文档曾记为固定 10702），随存档微变，疑存档计数/序号 |
| `+0x10` / `+0x14` | u32 = 700 | 球队记录数，与 1.2 节数组实测吻合 |
| `+0x20` | u32 = 98 | 8 样本一致 |
| `+0x30 ~ 0x50` | 32 字节哈希 | 样本间全变（diff 验证），游戏似乎不校验 |
| `+0x50` | u32 = 0x00194000 | 8 样本一致；指向 1.4 节区块 |
| `+0x54` | **用户球队名（UTF-8，NUL 结尾）** | 7/8 样本为「阿森纳」，ML2 为「ARSENAL」（语言设置差异） |
| `+0x9A ~ 0x9C` | ASCII「ARS」 | 与 +0x54 球队对应的 3 字母缩写，8 样本一致（**修正**：此前记为 +0x98，实测缩写首字节在 +0x9A，+0x98/+0x99 为 `00 00`/残留字节） |
| `+0xA0 ~ 0xFF` | 0 填充 | — |

### 1.2 球队记录数组（0x100 ~ 0x11F2C0）

- 700 条，每条 **0x690 (1680) 字节**；`0x100 + 700×0x690 = 0x11F2C0`。
- **口号字段存在系统性 off-by-one 错位（2026-08-29 修正，`bl_ml_probe26`）**：
  记录内 4 条口号槽 `+0x55/+0x65/+0x75/+0x85`（各 ≤16 字节 ASCII）。经 700 队全量核对，
  **每个队记录里的口号实际是「前一个队」（含用户队）的口号，而非本队**——
  即读取偏移差 1（shift-by-one）。证据（英超段连续 12 队全部命中）：
  AST(0 维拉)=GUNNERS/LONDON OUR CITY/ARSENAL FOREVER/GOONERS ON TOUR（阿森纳=用户队）；
  BRI(1)=AVFC VILLIANS/PRIDE OF BRUM（维拉）；BUR(2)=THE SEAGULLS（布莱顿）；
  CHE(3)=CLARETS/BURNLEY ON TOUR（伯恩利）；CRY(4)=CHELSEA（切尔西）；
  EVE(5)=CRYSTAL PALACE（水晶宫）；FUL(6)=TOFFEE ARMY/EVERTON（埃弗顿）；
  LEE(7)=FULHAM/COTTAGERS（富勒姆）；LEI(8)=LEEDS/LUFC（利兹）；
  LIV(9)=LCFC FOXES（莱斯特）；MCI(10)=YNWA/KOPITES（利物浦）；
  MUN(11)=MANCHESTER CITY/MCFC（曼城）。**只要把索引 +1（读取偏移补一位），口号即与球队正确对应。**
  成因推测：球队记录数组（700 队，不含用户队）与口号数组的索引基数差 1（0-based 队序 vs 含用户队的另序），导致 `team[i]` 读到 `team[i-1]` 的口号（i=0 时指向用户队阿森纳）。这与 `+0x598` 等字段同属"按偏移索引"布局，修正了此前"共享池、不能当真"的误判——口号与球队存在确定的一一错位对应，并非随机复用。
- **记录内队名字段（本轮新确认，`decode_dump.py` 700/700 全量验证）**：
  - `+0x5E4`：**中文队名**（UTF-8，NUL 结尾），如「阿斯顿维拉」「切尔西」；
  - `+0x62A`：**三字母缩写**（ASCII），如 `AST`、`CHE`；
  - `+0x630`：**中文球场名**（UTF-8），如「维拉公园球场」「斯坦福桥球场」。
  700 支球队全部可解（0 失败）。**用户球队（如阿森纳）不在该数组内**
  （PES2021 授权原因），队名仅见于头部 +0x54。
- 记录内 `+0x196` 起：一组 (u32, u32, u32) 三元组表（`+0x1A0` 处起
  `58 B0 00 00 / 01 00 00 00 / 03 AC 01 00 …`），u32 值域 ~0xB058，
  疑**队内球员 ID 或球衣/阵容索引表**（未解，见 3.2）。
- **队内动态字段**：BL0↔BL1 diff（`bl_ml_probe3.py` 节八）全部落在
  `+0x23E ~ +0x2D8` 范围（2105 字节、53 个偏移），主密集区
  `+0x23E~+0x258`——疑球队赛季状态（积分/排名/近期战绩类），未定名。
- 其余大部分记录体在样本间恒定（700 队静态资料）。

### 1.3 总体区块地图（非零数据带，≥1KB 零间隙切分）

`bl_ml_probe3.py` 节二，以 BL0 为例（ML 版边界几乎相同）：

| 范围 | 大小 | 内容判定 |
|------|------|----------|
| `0x000000 ~ 0xC1C6EF` | ~12.1 MB | 主数据区（头部+球队区+赛事表+球员/配置等，内部无大间隙） |
| `0xC1FAD4 ~ 0xC8A430` | ~420 KB | 重复字节块（`62 62 62…`/`72 72 72…` 交替），疑**球衣/纹理资源或压缩数据** |
| `0xC8B130 ~ 0xCA8A58` | 多个 1~20 KB 小带 | 零散结构（含大量 float 值域数据，见 2.3） |
| `0xCAAC90 ~ 0x1100EE5` (BL) / `0xCAAA93 ~ EOF` (ML) | 4.4~6.3 MB | 后段大数据区（浮点/能力值类为主，见 2.3；ML 延伸到文件尾） |
| `0x114036C ~ EOF` (仅 BL 有) | ~1.4 MB | 高熵区，样本间几乎全变，疑压缩块 |

要点：**0x11F2C0（球队区结束）与 0x194000 之间并没有大零间隙**，
属于同一主数据区；其间是 1.5/2.2 节的动态数据。

### 1.4 赛事定义表（约 0x1F1E30 ~ 0x200000）

`bl_ml_probe6.py` 节 A、`bl_ml_probe5.py` 节 F：

- 记录步长 **0x314 (788) 字节**；基址约 **0x1F1E30**（`FIFA世界俱乐部杯`
  记录在 0，表尾约 0x200000，76 个中文赛事名，对齐校验 72/76，
  不对齐者是双名/异常记录）。
- 记录内字段：

| 记录内偏移 | 内容 |
|------------|------|
| `+0x40 ~` | `00 00 FF FF…` 后接 **参赛实体 ID 列表**：u32，`FF FF FF FF` 为哨兵/空槽；列表前有 1~2 个小整数（1、2、3…疑计数/类型） |
| `+0x4C` | **赛事编号/条组 ID**（对齐 Lua 键池 `competition_id`）：值域 [1, 101]，62 独立值，同名赛事多记录共享同一编号（如多条“欧洲冠军联赛”记录均为 2） |
| `+0x50` | 小枚举 **[1..5]**（72 条内变动）：疑**赛事类型**（联赛/杯赛/锦标赛…）；另有两段 FF 主导的参赛实体列表区 `+0x58~0x108` 与 `+0x17C~0x1F8`（疑主场/客场或分队分组） |
| `+0x1FC` | 枚举 [0,1]：疑**是否可操作/用户参赛标记** |
| `+0x2C0` / `+0x2C4` | 枚举 [0..7] / [0,1,2,3,4,5,7]：疑**赛程模式/阶段配置**（对齐 `season_num` 参照系） |
| `+0x2C8` | **u16 赛季起始年**：BL0/BL1=`E4 07`(2020)、ML0/ML1=`E5 07`(2021)；BL2/BL3/ML13 为 `FF FF FF FF`（进度差异，该赛事未开赛标记）。验证：`python bl_ml_probe11.py C` |
| `+0x2CC`/`+0x2D0`/`+0x2D4`/`+0x2D8`/`+0x2DC` | 四个**金额候选槽**（量级 12 万~16 亿），但 BL0↔ML0 逐条几乎相同 → 静态配置（赛事奖池/默认预算档），非动态资金 |
| `+0x2E2` | **赛事全名（UTF-8 中文）**：欧洲冠军联赛、英格兰超级联赛、西班牙甲级联赛、社区盾杯… |
| `+0x2F0` 附近 | 第二字符串槽（疑赛事短名） |

- **证据**：76 个名串间距 68/75 恰为 0x314；ID 列表为连续递增小整数
  （如英超记录内 37 个连续队号 1..37，BL/ML 各异的分队段 38..75、76..113…，
  `bl_ml_probe4.py` 节四）；记录间 `FF` 填充与哨兵一致。
- 记录 `+0x4C` 起在 ML0↔ML13 间出现成片变动（0x1F2AD4 等），
  说明该表同时承载**当前赛季的赛事状态**，并非纯静态定义。

### 1.5 文件长度规律（外部信息）

- 原文件总长 = 320（加密头）+ 208（文件头）+ desc + logo + data + serial；
  **serial 区实际占字节 = 文件头 `serialLength` 字段 × 2**（按字符数计长，
  团队内已确认）。做总长核对/修改器时以此校正，勿把尾部多出的字节误判为
  data 的一部分。data 本身长度也随存档变化（19.52~19.74 MB）。

### 1.6 赛程表（比赛日记录数组，0x254 步长）

`bl_ml_probe9.py` D 发现、`bl_ml_probe10.py`/`probe12.py` C/`probe13.py` 固化：

- 记录以**日期三元组**为锚：`u16 年 + u8 月 + u8 日`
  （字节模式 `E4~E8 07 01~0C 01~1F`，覆盖 2020~2024），记录步长 **0x254 (596) 字节**。
- **基址与规模重大修正（本轮，`decode_dump.py` / 探针复核实测）**：
  两样本（BL0/ML0）真实基址均为 **0x3299B0**，表为 **13000 个定长槽位**的预分配
  整个生涯日历；空槽的序号字段为哨兵 `FF FF`（u32 读法同为 0xFFFF），顺序遍历至首空槽终止。
  **有日期的比赛日：BL0=10245 条（2020 年 3442 + 2021 年 6803，已赛 3055）、
  ML0=10205 条（2020 年 52 + 2021 年 6773 + 2022 年 3453，已赛 3031）**。
  此前“基址 0x345408（BL0）/0x3299B0（ML0）、713/1473 条”系扫描窗口
  [0x11F2C0, 0x400000) 与日期正则只认 2021~2023 双重截断造成的错误结论：
  0x345408 实为表内第 190 条记录（前 190 条为 2020 日期，被旧正则漏掉）。
- 记录内字段（以 BL0 为准）：

| 记录内偏移 | 内容 | 证据 |
|------------|------|------|
| `+0x30 ~ +0xDC` | 11 个 16 字节比赛条目：`[u32 match_id][u32 f2 偏移][u32 标志][u32 槽指针]`；match_id 空槽=`FF FF`；标志字节 0/1（疑已赛/未赛，对齐 `win_lose`/`proceed` 参照） | `probe15.py` B/A：BL0 rec0 条目 match_id=335,349,…，槽指针 ∈ 0x601E5A~0x625E5A |
| `+0x150` | u32 **槽位索引**：恒等于记录在表内位置，空槽=0xFFFF（**修正**：此前误判为“比赛日全局序号”，实为槽索引；旧值域 190→902/0→1472 只是截断窗口的产物） | `probe13.py` C + 本轮全表复扫 |
| `+0x158` | 日期三元组（如 2021-01-03） | 带内间距众数 596 = 步长 |
| `+0x160` | u32 轮次号（12/20/20…） | `probe12.py` C |
| `+0x174 ~ +0x224` | 11 个 16 字节**赛事实例条目**：`[u32 idx][u32 aux][u32=0][u32 槽指针]`，空槽 `idx=FF FF`；BL0 全表 5632 条、idx 值域 [0,18760]（疑全局场次号，对齐 `fixture`）；指针 ∈ [0x60195A,0x6260DA]，独立值仅 134（= 活跃赛事实例数） | `probe15.py` A |
| f2 字段（条目内 +0x04） | 指向动态区（0xA000~0x24000）的**索引/阶段表记录**：内容为异构堆块——索引表型（8 字节 `[08 00 00][u32 ptr][u8 seq]`，内层 ptr 再指阶段记录）与阶段表型（含 u16 队号列表 + `4B 00 00 00 37 8A 05 00 14 00 FF FF` 哨兵） | `probe15.py` B2/B3 |

- **主客队字段未定**：阶段记录内队号以“列表”形式出现（如 0x199B0 处 +0x20 起 26 个 u16 队号），非成对；对阵双方的直接字段需再沿 match 结果记录追（见 3.8）。

- 日期为真实比赛日：2021-01-03 一日 40 场（BL0）、2021-08-22 一日 42 场（ML0），
  分组规模符合全联赛赛程量级。
- **赛季前存档（BL2/BL3）**：本区全为 `FF FF 00 00` 哨兵（0 条赛程），
  且 0x345560 处记录着当前系统日期 2022-08-13（`E4 07 08 13`）——
  日期字段语义正确的负证据。
- **验证方法**：在 [0x11F2C0, 0x400000) 内搜日期正则，按 0x254 取模对齐定首条后，
  **向前扩展到最早记录**（宽日期正则覆盖 2020）即得真实表头 0x3299B0；再向后逐条
  遍历，至 +0x150 为 0xFFFF 的空槽终止。BL0 表头记录 #0 日期为 2020-08-22。
  （供与游戏 exe 对拍：记录长 596，日期在记录内 +0x158。）

### 1.7 赛事实例区（约 0x60195A ~ 0x6260DA）

`bl_ml_probe13.py` A、`probe15.py` A/B 固化：

- 1.6 表内两处指针均指向本区：+0x30 条目的槽指针（+0x0C）与
  +0x174 条目的槽指针（+0x0C）；BL0 独立槽址 134 个，值域 [0x60195A, 0x6260DA]。
- **槽内容 = 16 字节链式条目数组**（`probe15.py` B）：
  `[u32 标志][u32 指针][u32 a][u32 b]`，条目尾 `a=FF FF` 哨兵；
  标志值 0/1/0x10001；**a = 全局场次号**（如槽 0x601D5A 内
  a=0x3079~0x3089，值域与 +0x174 idx 同一空间 [0,18760]）；
  b 疑校验/种子（无单调性）。
- 条目内指针再指本区其他槽（嵌套链）或动态区堆块：已解出两类目标——
  ① 阶段/淘汰赛表（含 u16 队号列表，哨兵 `4B 00 00 00 37 8A 05 00 14 00 FF FF`，
  BL0 全文件唯一命中 0x1EF0C → 单条异构堆块而非定长数组）；
  ② 中文串记录（如 0x1EC67 处“某队”名串 + 指针 0x2D804B）。
- **验证方法**：取 BL0 赛程记录 #0 +0x174 首条目指针 0x601D5A，读 0x80 字节
  应见 `01 00 00 00 00 00 DA 9B 60 00 83 30 00 00 E0 B7 | 00 00 00 00 00 00 DA 1B 61 00 79 30 …`。
- 剩余未解：槽与赛事表的对应关系（疑按 competition_id 分组）、对阵主客队 → 3.8。

### 1.8 全库球员名串负判定（存档不存球员资料）

`bl_ml_probe7.py` A、`bl_ml_probe8.py` B、`bl_ml_probe9.py` A：

- 全文件大写「FIRST LAST」名串：BL0=613 / ML0=611 个，**全部落在球队区口号**
  （0x100~0x11F2C0），后段大带（0xC80000~EOF）零命中。
- 后段带 UTF-16LE 名串：0 命中；UTF-8 中文命中 11/30 处均为 float 字节巧合误报。
- 0xB00000~0xC80000 内中文串：每个样本**仅 1 处** = 用户球员记录（2.1）。
- **结论：data 块不存全库球员资料（姓名/能力值），应来自游戏外部数据库；
  data 内只有球员 ID 空间的动态值**（用户球员 ID 143939、参赛实体 ID 1..219、
  球队记录 +0x196 三元组 ~0xB058 等）。
- **exe 侧交叉确认**（`docs/exe_analysis.md` 第八节）：游戏从
  `cpk_dat/common/etc/pesdb/` 加载 Player.bin 等 28 张外部表——本负结论与
  exe 静态分析交叉成立。
- **验证方法**：`python bl_ml_probe7.py A`、`python bl_ml_probe9.py A`，
  期望后段带真实名串为 0；后续与 exe 中的外部数据库加载逻辑对拍。

## 二、疑似结构（单一证据，待验证）

### 2.1 用户球员记录（BL，0xB7E2xx 附近）

`bl_ml_probe6.py` 节 C；本轮字段修正（`decode_dump.py` 实量）：

- **记录起点 0xB7E2C0**（中文名锚点 0xB7E2C9 前 0x0C）：
  `u32@+0x00`=3722（较小整数，疑内部序号/索引），
  **球员 ID 在 +0x04 与 +0x08 两处**（均为 143939，
  **修正**：此前误把 0xB7E2C0 直接记为球员 ID 位置）。
- `0xB7E2C9`：**中文名（UTF-8）「达里奥·埃苏戈」**（含 C2 B7 中点）。
- `0xB7E309`、`0xB7E346`：**ASCII 名 `DARIO ESSUGO` 两份**（相距 0x3D，
  疑「显示名 + 注册名」或「名 + 姓」双槽）。
- 名字之后（`+0x70` 起）：一串带 `0280`/`0340` 高位标志的 u16
  （`22 00 80 02`、`29 00 80 02`…），随后 `FF FF 00 00` 空槽阵列——
  疑**球员能力/属性索引表**。
- `0xB7E3CC`：`E7 07` = **2023**（u16 年），后随 `01 1F`；
  `0xB7E3FC`：`E5 07 01 04`（2021 + 0x0401）；`0xB7E434`：`E5 07 00 00`。
  疑 **u16 年 + u16 打包月日** 的日期字段（合同/转会期）。
- `0xB7E414 ~`：`07 00 00 00` ×7，疑球衣号/位置偏好重复项。
- 判定依据：真名实姓（Dário Essugo 为真实球员）+ 中文名 + 年份字段集中；
  记录边界本轮已用字段对齐确认（起点=锚点-0x0C，ID 双备份）。
- 补充（本轮修正）：ML0 的同型记录起点在 **0xB7F2F0**（中文名锚点 0xB7F300
  「阿莱克斯」前 0x10，此前误记为 0xB7F2FC）；其前方 0xB7F2E0 有四个 u32 头字段
  （671, 1, 681, -11）；该记录**无 ASCII 名**（全文件搜索确认）。说明该记录每存档一条、
  位置不固定；BL2/BL3 的 0xB7E3CC 处日期为 2022-01-31（疑用户球员建档/生日）。

### 2.2 0x194000 区块：阵型/战术表

- 头部 `+0x50` 指针直指此处；8 样本前 64KB 差异 0~5063 字节
  （BL0/BL1 完全相同、ML 系略有差异），**大部分恒定** → 静态配置为主。
- 区块头：`00 00 00 00 10 00 00 00…`；内容以小整数对为主
  （`34 19 44 19 24 23 54 23 14 2B` 等，形如 (位置/号码, 球员索引) 对）。
- 区块内散布 `FF FF F7 07` 模式（≥6000 处，众数间距 4 字节）——
  `F7 07` = 2039，疑**空槽哨兵值**而非记录边界。
- 判定：疑为 700 队的**默认阵型/战术/定位球配置表**；记录步长未定。

### 2.3 0x11F2C0 ~ 0x194000：float 数组 + 小整数排列表

`bl_ml_probe4.py` 节二、`bl_ml_probe6.py` 节 D：

- 非零占 64.7%，值分布以 `FF`/`01`/`34`/`0B`… 为主，32 字节 run 重复
  5399 次（`01 01 03 02 04 04 07 06 08 0C 03 34 0A 3F…`）——
  形如**默认战术模板的 16 对 (x,y) 或 (角色,号) 数组**，700 队复用。
- 散布 16~49 字节的小整数（0~0x27）洗牌序列，跨样本重排 →
  疑**赛程顺序/抽签结果**。
- ML0↔ML13 在本区的大量变动值呈 2^24、2^16、2^8 量级步长 →
  实为 **float32 数组**（能力/评分/财政系数类），非整型金额。
- 判定：本区是"每队一份的配置 + 当前赛季动态值"混合区，未分表。

### 2.4 后段 4.4~6.3 MB 大带（0xCAAC90 起）

- 字符串扫描只见零星伪文本（`3BQA` 等 = float 0x415142xx 的 ASCII 映像），
  判定主体为 **float 数组**（球员能力值/曲线/经济数据的大表）。
- 4 字节对齐周期搜索无重复记录头 → 不是定长记录数组，
  可能是多维矩阵或按索引表引用的块。
- `probe9.py` B：BL 后段大带 113.7 万 u32 槽中小整数占 21%、有效 float <1%，
  大量 `00`/`FF FF FF FF`/`FF FF 00 00` 模式 → 更像“稀疏索引表”而非纯能力值矩阵。

### 2.5 球队记录 +0x590~+0x59C：转会预算字段簇（2026-08-29 由 exe 侧证据升档）

`bl_ml_probe11.py` B、`probe12.py` A、`probe13.py` B：

- 记录内 `+0x598`：u32 全为万位整数，700 队分布：0×203、10000×250、
  30000×70、50000×73、100000×45、300000×33，**8 样本完全一致**（静态默认值）。
- 若按“万”为单位即 0~7 亿，量级与 PES 大师联赛转会预算相符；
  邻近字段 `+0x590`=小整数 (0/1/2)、`+0x594`/`+0x59C` 也是万位整数（60800/100000 等）。
- **为何留在疑似**：静态不随进度变化，可能是“初始预算”而非当前余额；
  且球队 33 在 `+0x5B4` 的 -65321（有符号）未见离群，该偏移已排除。
- exe 侧资金入口字符串（`MLBudgetSetting/MLBudgetReport/MLSeasonSalary/
  MLAcountingTransferFeeDetail` 等，见 `docs/exe_analysis.md` 8.2）未含“余额”
  字段名，与“动态余额非常规存储/计算得出”的盲定位负结果吻合。
- 验证方法：任意队 N，读 `0x100 + N×0x690 + 0x598`（u32）；期望为万位整数。

**2026-08-29 升档结论（无需游戏内数值，来自 exe 静态反汇编）**：
`docs/exe_money_analysis.md` 解出游戏货币汇率表，欧元档系数 = **100**，
即"存档金额 × 100 = 欧元显示值"。据此 `+0x598` 的取值换算后为
**100 万 ~ 9000 万欧元**（50000→500 万、300000→3000 万、900000→9000 万），
与大师联赛各级别俱乐部转会预算吻合 → **`+0x598` 由"疑似预算"升档为
"转会预算（初始/赛季初分配值）"**。
`bl_ml_probe17.py` 实测：ML 样本中该字段万位整数占比 **71.0%**（700 队），
且在赛季前存档 ML00000002 中**恒为 0**——与"赛季未开始则预算未分配"一致。
注意：**这是初始分配值，不是当前余额**；当前余额的下落见 3.1 的新假说。

### 2.6 动态事件表 @ 0x12A72FD（2026-08-29 发现，`bl_ml_probe21/22/23/24/25`）

在"非赛程表"日期三元组扫描中，于 `0x12A72FD` 命中一个**定长数组**：

- **记录布局**：步长 **0x24 (36 字节)= 9 个 u32**，首 4 字节为日期三元组（`u16年+u8月+u8日`）。
- **动态性已确认**：赛季前存档 ML00000002（preseason）同区**完全无日期表（0 条）**，与"赛季未开始则无交易/事件"一致 → 是**赛季中运行时动态生成**。
- **跨样本对比（in-season）**：ML0/ML1/ML13 均为 **100 条**（含 1 个哨兵槽：f1/f7 为 0xFFFFFFFF/0xAB… 巨型值），真实事件 **99 条**。日期覆盖 **2021-08-16 → 2021-09-02**，单调不减。容量固定≈100 的**环形缓冲 / 最近事件滚动窗口**（ML13 起止日期更晚、f2 高16位相异数降到 33，印证覆盖/复用），而非无限累积流水。
- **字段语义（`bl_ml_probe24/25` 统计推断）**：

| 字段 | 偏移 | 观测 | 推断 |
|------|------|------|------|
| date | +0x00 | u16年+u8月+u8日，覆盖 ~2021-08-16→08-31 | 事件日期（同日可多笔，非严格递增） |
| `f1` | +0x04 | {0:85, 1:14} + 1 哨兵；真实 99 条为 0/1 | 事件类型/方向标志（0 均值 f4≈2535万，1 均值 f4≈8.5万） |
| `f2` | +0x08 | 高 16 位 = 球员登记 ID（ML0/ML1 覆盖 1860~64867、ML13 仅 33 个相异值）；低 16 位为变化值（**非**恒 0xFFFF） | 高16位=球员登记 ID；低16位=次要字段（序号/状态） |
| `f3` | +0x0C | 99 条中 80 条 ×100 后落入 3.4千~4.29e8；含个别巨型值（哨兵 0xFFFFFFFF） | 次要金额 / ID 候选（转会费或球员 ID） |
| `f4` | +0x10 | 99 条中 96 条 ×100 后 9.8万~4.29e8；无负号、无 0xFFFFFFFF 空值 | **最像金额（转会费），×100=欧元**；方向由 f1 而非符号区分 |
| `f5` | +0x14 | 99 条中 52 条落在区间；量级可达 1.07e9×100 | 第二金额（工资/累计？） |
| `f6` | +0x18 | **f7==1 时恒为 0xFFFFFFFF（空）；f7==0 时为具体值** | 条件字段（仅"有效/已完成"记录携带） |
| `f7` | +0x1C | {0:86, 1:13} + 1 哨兵；f7==1 必 f6=0xFFFFFFFF | 状态位（0=已结算/有效，1=挂牌/待定/未完成） |
| `f8` | +0x20 | 小整数（0~数万） | 计数器 / 次级类型 |

- **金额闭合（未解）**：`f4` 全为绝对值正数、方向由 f1 区分，与"余额 = 初始预算(+0x598) + 流水汇总"假说兼容。但**本表已确认是全局转会活动日志（非单一俱乐部账本）**——见 §2.9 跨存档验证。缺少"玩家所属俱乐部→记录"的映射，暂无法在纯数据侧做 Σ 闭合；需先建立该映射（或定位存档内"玩家队"索引）才能校验。
- **结论**：本表极大概率是 `MLAccountingTransferFeeDetail` / `MLAccountingSalaryDetail` 所指的**转会/收支事件明细**（动态、按日期、含金额与状态位）。字段语义仍属统计推断：最终确认需逆向写出例程——但 `FL_2023.exe` 中 `MLAccounting*` 无 C++ RTTI 引用（原生侧已证伪），`Assembly-CSharp.dll` 不在仓库、`CmnTransferMarket` xref 路线亦失败。下一步须从 CPK 提取游戏数据表，或先建立俱乐部映射再做闭合。

### 2.7 运行期资金偏移（来自 exe 反汇编，`exe_aob.py` / `exe_xref.py`）

- `INJECT_ClubBudget`（CT 表 AOB `8B 87 F4 CB 6E 01 89 45 C4`）精确定位在
  **VA 0x140EA4C58**（RVA 0xEA4C58）。该函数是 Edit Club Budget 对话框的事件处理：
  反复 `mov 0x16ECBF4(%rdi),%eax` 把 transfer budget 读入控件变量。
- 由此确认内存中 ML 全局数据对象内的字段偏移：
  **transfer budget = +0x16ECBF4**，**salary budget = +0x16ECC08**（二者相差 0x14，成对）。
  这是**运行期余额/预算快照位**（非团队记录内的 +0x598，后者是存档的初始分配值）。
- 反汇编未在该函数附近发现"流水数组"循环；预算与薪资以**相邻成对**字段形式存在，
  进一步支持"当前余额 = 初始预算(+0x598) + 收支流水汇总"的运行时计算模型。

### 2.9 事件表跨存档验证与玩家队定位（2026-08-29 晚，`bl_ml_probe31/32/33/34`）

在「停解包、纯数据侧」约束下，对 `decoded/` 中 ML0/ML1/ML13（in-season）与 ML2（preseason）重做解析，产出校正表头后的干净表 `outputs/event_table_clean.csv`（每次 99 条真实记录，ML2 为空）。

**1. 事件表性质：确认是全局转会动态 feed，而非玩家队专属流水。**
- ML0/ML1/ML13 三条存档的 `v3/v4/v5/v6/v8` 字段分布**逐字节一致**（同值域、同高频值）；若为玩家队专属账本，俱乐部相关字段应随不同生涯（不同用户队）而变化。
- 跨存档 `f2_hi`（球员登记 ID）交集 = **0**，并集 231。各档互为独立生涯、各自世界模拟产生不同转会活动窗口（2021-08-16→08-31），符合 §2.6 的"最近事件滚动窗口"，而非固定子集（如玩家阵容）。
- `v1` 分布恒为 `{0:85, 1:14}`（`f7` 恒为 `{0:86, 1:13}`）——85=已结算、14=挂牌，与"全球转会新闻/挂牌动态"一致。

**2. `v4`/`v5` 不是简单俱乐部 ID。**
- `v4` 值域 `[983, 1.07e9]`，`v5` 值域 `[1.6e6, 1.07e9]`，远超合理俱乐部序号（1..700）；疑似打包值或指针，无法据此直接过滤玩家队。

**3. 玩家队（my-team）定位：当前阻塞点，未在球队数组内找到。**
- 球队块（0x100 起、步长 0x690、700 队）。`+0x598` 预算非 0 的队共 **497** 支（如 team#0=700000、team#8=100000 等；原始值，单位待定）。
- 以「整 stride 内仅一队非零」为判据做 1/2 字节粒度扫描，三档交集中命中的偏移**均指向同一支真实俱乐部**（如 +0x2D8 恒为 team#399）——属该俱乐部的私有块/指针，而非玩家队标志。
- 换言之：**玩家队不在球队数组里用「唯一标志位」存储**，更可能在某个全局配置区记录"用户所选队号"。此索引未在当前解析中定位到，是预算 Σ 闭合的关键阻塞。

**4. 闭合所需的最小前置条件（仍待补）**
- (a) 玩家队索引（全局区，非球队数组）；或
- (b) 已可读的 dt10/pesdb（`Team.bin`/`PlayerWeekly.bin` 等）→ `注册ID ↔ 实体` 映射 + 事件表内俱乐部字段（v4/v5）的字段级解码。
任一打通即可把事件表按玩家队过滤，再用 `f1`/`f7` 区分收支 方向与 `+0x598` 初始预算做 Σ 校验。`dt00` 为音频包，不在此链路内。

### 2.10 球员「注册 ID → 名字」反查（route A，2026-08-29 深夜→收尾，`bl_ml_probe35`→`bl_ml_probe46`）

**旧结论（probe35 阶段）"route A 架构性阻塞"已被推翻**：用户随后把 `EDIT00000000` 放入 `examples/`，据此打通了名字反查。完整链路如下。

**0. 解密 EDIT 存档（关键前置）**

**1. EDIT 球员名表结构（stride-312 = data 240B + appearance 72B）**

## 四、修改器视角的注意事项

1. data 长度可变（尾部填充不同），写回时保持原长度或按游戏实测调整。
2. 球队/赛事表内大量 `FF` 哨兵，改动时保留哨兵语义。
3. 0xC1FAD4 起的资源块与 0x114036C 高熵区按不透明块处理。
4. 头部 +0x30~0x50 哈希目前看非强制，但稳妥起见改动后做进游戏实测。
5. 赛程表（1.6）内含**绝对指针**指向赛事实例区（1.7）：搬移/插入记录时必须
   同步更新指针，否则进游戏崩溃；赛季前存档（如 BL2/BL3）无赛程表，
   写入前先确认基址是否存在（搜日期三元组）。
6. 赛程记录内两处条目区（+0x30 与 +0x174）的槽指针指向**共享的 134 个实例槽**
   （BL0），槽内又是嵌套链：任何增删比赛条目的操作都会牵动实例区链结构，
   修改器建议只改字段值、不改条目数量；异构堆块（阶段表/索引表）无定长步长，
   不可按固定数组批量写入。
